01

The premise

Most agent tooling is a black box that talks to a server you cannot inspect. This is the opposite shape: a composition root you can read end to end, a daemon that binds to 127.0.0.1 and refuses anything else, and an offline provider that works before you configure a single key.

It is generic. The core knows about Provider, Agent, Session, Project and Tool — not about any vendor. Any host application is one adapter among several, and the core does not know any of them exist.

  • Dependency-free core. Node standard library only, so every behaviour is auditable in the repository.
  • Runs offline. The network is reached only when a provider you explicitly configure requires it.
  • Honest integrations. A configured-but-unreachable integration reports why instead of a fake ok.
  • Secrets by reference. $ENV_VAR or envfile:<path>. An inline literal is refused at the resolver.
02

The shape

 host application
    │  normal operation, unchanged — its own auth, its own servers
    │
    └── .agents/mcp.json  ──stdio JSON-RPC──▶  MCP adapter
                                                    │  HTTP 127.0.0.1 + token
                                                    ▼
                                            local daemon ──▶ runtime
                                                              │
                        agents · sessions · projects · tools · context · memory
                        providers · models · MCP · workflows · events

Two process boundaries, one protocol. The MCP adapter is deliberately stateless: it translates each call into a daemon HTTP call instead of holding runtime state, so a host can restart it freely and lose nothing.

One installer, idempotent by construction

Every step reports created, updated, unchanged or skipped. Running it twice changes nothing the second time — because an installer you cannot safely re-run is not an installer.

Survives a reboot, then proves it

A Windows logon task supervises the daemon in the foreground with an unbounded failure budget. Measured cold restore from nothing: 3.0 s to a live /health and a full readiness verdict.

Least privilege by default

Capabilities are denied unless a rule grants them, longest scope wins. A per-invocation grant applies to that call only and never widens the session. No write, delete or spawn tools ship.

Redaction at the sink

Every value leaving the process passes through one redaction point, every SSE frame through one framing function. Secrets are never stored at rest in the repository.

03

The boundary

Not preferences. Changing any of these breaks the premise.

1

No interception

The runtime serves an MCP server. It never reverse-engineers, impersonates, proxies, intercepts or redirects a host's traffic. The host keeps running its own servers, untouched.

2

No telemetry

telemetry is typed false. Setting it true is a hard configuration error, not a warning. No field reports outward.

3

No secrets in the repository

Secrets are referenced as $ENV_VAR or envfile:<path>. The resolver refuses an inline literal, so a secret cannot be committed by accident.

4

Loopback only

A non-loopback bind host is a configuration error. Any request carrying an Origin header is refused, and a non-loopback Host header is refused as a DNS-rebinding guard.

5

Default-deny

Capabilities are denied unless a rule grants them; longest scope wins. MCP tools require mcp.use, which is denied by default.

6

Private, unlicensed, never published

Not on any registry. Nothing is uploaded. This site is the only public surface, and it carries no data.

All three POST surfaces accept the same token as x-agent-sdk-token, Authorization: Bearer, or x-api-key — so a client that can only set one of those still authenticates. /health is the only unauthenticated route.

05

The oracles

Exit code 0 from a script that started nothing is the failure mode this whole design exists to eliminate. So success here means something was observed from outside the process.

#oracleprovesfailure mode it was written for
1 /health observed over HTTP a socket answered from outside the process a daemon that exited 0 without binding
2 doctor --json → readiness.ok every component reported itself reading components from the wrong object path
3 resident verdict in the supervisor log the integration actually started a supervisor built to carry on when the resident fails
4 registration resolves on disk a fresh session can reach this build a stale path that still lists tools and dies on first call
5 probe.ok: true host → adapter → daemon → provider → response /health proving nothing about the model
6 tracked tree carries nothing local-only the published repo names nothing private a committed .gitignore publishing the very folder it hides

Anchors come from the same writer as the evidence

Oracle 3 once anchored to the scheduler's LastRunTime, which can be stamped after the supervisor process wrote its verdict. A warm re-run then filtered out a genuine pass and reported failure on a perfectly healthy stack. The fix was not a wider tolerance window: the supervisor now stamps an instance id as its own first log line, and the oracle anchors to that. Same writer, same clock, no skew.

06

Install

git clone <this repo> agent-sdk-pimo
cd agent-sdk-pimo
npm install
npm run build

npm run setup        # build, install, supervise at logon, prove it

install registers the MCP server at user level, so any host in any directory finds it, and it starts the daemon — so you never have to run daemon start yourself.

npm run verify:registration

Read-only. Reads the registration a host will actually read and touches the filesystem for every hop. No writes — a diagnostic that repairs what it is diagnosing cannot be trusted to report.

npm run prove:plug-and-play

Cold spawns the entry point from a directory this runtime has never seen, with no daemon running, and asserts the real handshake plus a real generation.

npm run verify:hygiene

Read-only. A .gitignore is committed and served to anyone, so a line naming a private or per-machine folder publishes the name it hides. Those patterns live in .git/info/exclude, which git never commits. This proves the tracked tree carries nothing local-only and that the split has not drifted.

What is not claimed here

No real reboot has been performed, so the logon trigger itself is unproven — what is proven is that the task's action restores the stack from nothing in about three seconds. One integration suite has a pre-existing failure unrelated to this work and is left untouched. Where an integration is configured but unavailable, the runtime says so and explains why instead of pretending.
